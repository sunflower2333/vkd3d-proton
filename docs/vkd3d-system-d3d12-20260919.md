# Ordinary D3D12 admission and allocation requirements

The native UMD still cannot admit ordinary Microsoft D3D12 applications. Its
adapter version enumeration returns zero, caps are unsupported, and table
publication is guarded by the incomplete native contract. Exporting
`OpenAdapter12` or passing an emulated-runtime callback test does not bypass
those requirements.

## Implemented prerequisite

The R0 `pfnCheckResourceAllocationInfo` field now queries the embedded backend's
real allocation requirements for the currently supported native buffer and
single-mip/layer/sample R32_FLOAT or RGBA8 non-RT/DS texture shapes. A query
retains the device, copies input, drops callback locks across the backend call,
checks retirement, and publishes the output once. It never allocates KMD
storage. Invalid flags, node masks, unsupported alignments, backend failure and
retirement report failure without modifying caller output.

The query does not add public fences, monitored queue signal/wait, residency,
GPUVA, graphics pipeline/draw or Present contracts. Capability/table admission
remains closed. These missing pieces must be completed and integrated before
ordinary D3D12 device creation can succeed.

## Ordinary application probe

`vkd3d-system-d3d12-probe.exe` includes only public Windows SDK headers. It loads
the system DXGI and D3D12 DLLs from System32; it does not link the embedded vkd3d
backend, call UMD exports, substitute runtime callbacks, or implicitly select
WARP. Its PE dependencies are checked during packaging.

Root can stage only this architecture-matched executable from the CI package
and run the shortest admission test:

```text
vkd3d-system-d3d12-probe.exe --list
vkd3d-system-d3d12-probe.exe --luid-low LOWHEX --luid-high HIGHHEX --run-device
```

Use the fresh hardware adapter's printed low/high LUID words. The executable
rejects a software adapter and checks the device LUID. It prints module paths
and the exact failing stage/HRESULT. With this candidate's closed native gate,
a failure at `D3D12CreateDevice(FL11_0)` is expected; only target execution can
establish the actual installed-package result and HRESULT.

When admission is implemented, the next ordinary-app test is:

```text
vkd3d-system-d3d12-probe.exe --luid-low LOWHEX --luid-high HIGHHEX --run-copy
```

This creates a public queue, allocator, command list, upload/default/readback
resources and fence. Four rounds change the input, copy through the default
buffer with nonzero source/destination offsets and state transitions, signal a
public fence, wait up to ten seconds, and verify all 1,024 output words per
round (512 copied words and 512 untouched sentinels). The successful copy marker
explicitly excludes graphics and Present acceptance. Use a process deadline
when running the test on a candidate driver.

## Validation boundary

`--run-warp-ci` explicitly selects CPU WARP solely to validate the ordinary
application harness on CI. Its success marker says `CPU_WARP_HARNESS_ONLY` and
`no VIOGPU acceptance`. Windows native callback fixtures cover allocation-info
requirements, no-allocation behavior, input poisoning, rejected-output
preservation, backend failure and retirement. Linux CPU Vulkan checks the
buffer requirements against the real backend. These tests must not be reported
as VIOGPU target acceptance.
